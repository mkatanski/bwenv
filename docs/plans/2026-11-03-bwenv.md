# bwenv Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A Bun/TypeScript CLI, `bwenv`, that keeps a project's local `KEY=value` secret files in step
with a private Bitwarden vault, plus a Claude Code hook that keeps agents out of those files.

**Architecture:** The manifest (`bwenv.json`) in each project says what exists and where it goes. The
`bw` CLI, wrapped and always run with `--nointeraction --response`, holds the values. Pure modules
handle the dotenv text, the manifest, the sync decision table and the guard rules. Thin command
modules wire them to the vault and the disk. Integration tests drive the real CLI against a fake `bw`.

**Tech Stack:** Bun 1.4.4. TypeScript 6.0.2 through `npm:@typescript/typescript6@6.0.2`, because
typescript-eslint 8.72.1 requires `typescript <6.1.0`. eslint 10.14.0, @eslint/js 10.0.1,
typescript-eslint 8.72.1, prettier 3.9.10, @types/bun 1.4.4. There are no runtime dependencies.

**Spec:** `docs/designs/2026-11-02-bwenv.md`. Read it before any task. Each task refers to it by
section.

## Global Constraints

- No runtime dependencies. Only Bun and `node:*` built-ins.
- No `any`: use `unknown` and narrow it. Inline ESLint directives are impossible because
  `linterOptions.noInlineConfig: true` is set. `index.ts` files may only re-export, and none is
  planned.
- Comments only where a test or a name cannot carry the meaning.
- **A secret value never appears** on stdout or stderr, in an error message, or in the argv of any
  child process. The session key reaches `bw` only as `BW_SESSION` in the child's environment.
  Encoded JSON reaches `bw create` and `bw edit` only on stdin.
- Every `bw` call except `unlock` is `bw --nointeraction --response <...>`. A success response is
  `{"success":true,"data":...}` and a failure is `{"success":false,"message":"..."}` with exit 1
  (observed 2026-11-02). For `status`, the data sits at `data.template.status`, with the values
  `unauthenticated`, `locked` or `unlocked`. For `list`, the array sits at `data.data`.
- The `bw` binary is `process.env.BWENV_BW ?? 'bw'`.
- Agent refusal: when `CLAUDECODE === '1'`, `sync`, `add`, `update`, `rm` and `list --vault` throw
  before any `bw` call.
- Value pattern `^[A-Za-z0-9_\-.:/@+=,%]+$`. Name pattern `^[A-Z_][A-Z0-9_]*$`. Project and
  environment pattern `^[a-z0-9][a-z0-9-]*$`. The default environment is `local`.
- Vault folder `bwenv/<project>`. Item names are `<project>/<NAME>`, or `<project>/<env>/<NAME>` when
  the variable is `perEnvironment`. Item type Login (`type: 1`), `login.username = NAME`,
  `login.password = value`.
- The state file is `${XDG_STATE_HOME ?? ~/.local/state}/bwenv/state.json`, mode `0600`, and stores
  sha256 hex hashes, never values.
- Secret files and the state file are written to a temporary file in the same directory, chmodded to
  `0600`, then renamed into place.
- Exit codes: `0` success, `1` something needs attention, `2` wrong usage.
- Commits: one Conventional Commits line, no body, no trailer, **no attribution of any kind**, and no
  `--author`.
- Formatting: Prettier with `semi: false` and `singleQuote: true`.

## Review Focus

1. **A file with CRLF endings, `export KEY=value` lines, duplicate keys or no final newline.**
   `setKey` keeps every other line byte for byte, keeps the `export ` prefix and the file's line
   ending, and leaves exactly one occurrence of the key. Tested in Task 1.
2. **A value piped from `pbpaste` or `echo`, which carries a trailing newline.** One trailing
   `\n` or `\r\n` is stripped. An empty value is refused before anything is written. Tested in
   Tasks 5 and 7.
3. **`bwenv` run from a subdirectory of the project.** The manifest is found by walking up, and
   relative `file` paths resolve against the manifest's directory, not the current directory. Tested
   in Tasks 2 and 5.
4. **Two vault items with the same name** in the folder, for example one created by hand. bwenv stops
   and names the duplicate rather than picking one. Tested in Task 4.
5. **A hand-edited `bwenv.json`** with invalid JSON, a typo'd field such as `perEnviroment`, or a
   bad name. The error names the file and the field, and exits 2. Tested in Task 2.

- Produces, in src:
  - `interface VaultItem { id: string; name: string; value: string | null; raw: Record<string, unknown> }`
  - `openVault(options: { env: Record<string, string | undefined>; isTTY: boolean; ownerCommand: string; stderr: { write(s: string): unknown } }): Promise<Vault>`
  - `class Vault`, with:
    - `folderId(project: string, create: boolean): Promise<string | null>`
    - `items(folderId: string): Promise<VaultItem[]>`
    - `findItem(items: VaultItem[], name: string): VaultItem | null`
    - `createItem(folderId: string, name: string, username: string, value: string, notes: string): Promise<void>`
    - `updateValue(item: VaultItem, value: string): Promise<void>`
    - `deleteItem(id: string): Promise<void>`
  - `assertNotAgent(env: Record<string, string | undefined>, ownerCommand: string): void`

**The fake's behaviour:**
- It records every call.
- It counts as unlocked only when the vault is `locked` **and** `BW_SESSION === session`. Otherwise
  every data command answers `{"success":false,"message":"Vault is locked."}` with exit 1.
- `status` answers in the real shape.
- It implements `sync`, `list folders [--search s]`, `list items --folderid id`, `create folder`,
  `create item`, `edit item <id>` and `delete item <id>`. The last three decode the base64 JSON from
  stdin. `delete` sets `deletedDate` and hides the item from `list`.

**The `openVault` order:**
1. `assertNotAgent`, which throws exit 1 with
   `bwenv does not open the vault for an agent. Ask the owner to run: ${ownerCommand}`.
2. `status`:
   - `unauthenticated`: exit 1 with `The Bitwarden CLI is not logged in. Run: bw login`.
   - `unlocked`: use `env.BW_SESSION`.
   - `locked` with a TTY: spawn `bw unlock --raw` with stdin and stderr inherited and stdout piped,
     then write `Tip: export BW_SESSION=$(bw unlock --raw) in your shell to skip this prompt.` to
     stderr.
   - `locked` without a TTY: exit 1 with
     `The Bitwarden vault is locked. Unlock it in your shell: export BW_SESSION=$(bw unlock --raw) — then run this again.`
3. `sync`.

  - `create, find, update and delete round-trip`:

    - after `deleteItem` it is gone.

  - `duplicate names stop`: two raw items named `p/A` make `findItem` throw exit 1 with a message

| Condition | Outcome |
|---|---|
| `vault === null` | `missing` |
| `local === vault` | `unchanged` |
| `local === null` | `write` |
| `force` | `write` |
| `lastWrittenHash === hashValue(local)` | `write` |
| otherwise | `conflict` |

**`runSync`:**
1. Resolve the env: `--env` if given, otherwise `defaultEnvironment`, checked against `ENV_PATTERN`.
2. Group the variables by resolved file. `--file` filters the groups by resolved path, and a `--file`
   that matches nothing is exit 2.
3. Open the vault and run `folderId(project, false)`. A missing folder makes every variable `missing`.
4. For each file:
   - Run `assertIgnoredIfInRepo`. If it fails, report the file and skip it.
   - Apply the `write` outcomes with `setKey`, and write once if anything changed.
   - `recordValues` the `write` and `unchanged` keys with the env.
5. Report one row per variable:
   - `written`
   - `unchanged`
   - `conflict — changed by hand since the last sync. Keep yours: bwenv update NAME --from-file · Take Bitwarden's: bwenv sync --force`
   - `not in Bitwarden — <how>. Then: bwenv add NAME`
   - for a missing `perEnvironment` variable: `not in Bitwarden for <env> — ...`
6. Exit 1 if any row was a conflict, a missing value or a skipped file.

  - `decideSync` gets one test per row of the table, including no record with a differing local
    value, which gives `conflict`.
  - Integration, against vault items from `writeVault`:
    - `sync writes every declared value and records hashes`. The file ends with `A=va\nB=vb\n`, the
      file mode is `0600`, and the state has both hashes and env `local`.
    - `sync keeps unrelated lines`. A pre-existing `# note\nOTHER=1\n` survives.
    - `hand edit is a conflict and is left alone`. Sync, then edit `A` by hand, then change the vault
      value and sync again. The run exits 1, the file keeps the hand value, and stdout contains
      `conflict` and `bwenv update A --from-file`.
    - `pre-existing differing value with no record is a conflict`.
    - `--force takes the vault value`.
    - `missing in vault keeps the local value and prints how`. The run exits 1, the local `A` is

### Task 9: The guard: `is-secret` and `hook claude`

**Files:**
- Create: `src/guard.ts`, `src/commands/guard.ts`
- Test: `test/guard.test.ts`, `test/hook.test.ts`

**Interfaces:**
- Produces:
  - `interface GuardContext { cwd: string; home: string; statePath: string }`
  - `isSecretPath(path: string, ctx: GuardContext): boolean`
  - `judgeBash(command: string, ctx: GuardContext): string | null`, which returns the denial reason
    or null.
  - `judgeToolCall(input: { tool_name: string; tool_input: Record<string, unknown>; cwd?: string }, ctx: GuardContext): string | null`
  - `runIsSecret(ctx, args)`: exit 0 when the path is secret, 1 when it is not.
  - `runHook(ctx, args)`: `hook claude` reads the hook JSON from stdin. On a denial it writes the
    reason to stderr and **exits 2**, which is how a Claude Code `PreToolUse` hook blocks a call.
    Otherwise it exits 0. Unparseable input exits 0 and writes `bwenv hook: unreadable input` to
    stderr; the hook fails open so that a bug never blocks every tool.

**`isSecretPath`:** spec § *Commands*, `is-secret`. It checks, in this order:
1. Built-in names: `.env`, `.env.*` except `.env.example`, `.dev.vars`, `.dev.vars.*`.
2. The keys of the state file.
3. The manifest found from `ctx.cwd`.
4. The manifest found by walking up from the path itself.

Paths are resolved against `ctx.cwd`, and `~` is expanded.

**`judgeBash`:** spec § *Commands*, `hook claude`.
- **Splitting:** segments split on `|`, `&&`, `||`, `;` and newlines. Words split on whitespace,
  respecting single and double quotes. Leading `NAME=value` words are skipped to find the command
  word.
- **Expansion:** `~`, `$HOME` and `${HOME}` are expanded, and `--x=value` is split at the first `=`.
- **The reading list:**
  `cat less more head tail grep rg ag sed awk cut sort uniq diff cmp bat xxd od hexdump strings base64 cp mv tee jq vi vim nvim nano code open pbcopy`
- **Denials:**
  - a command word of `bw`, or ending in `/bw`:
    `Agents do not use the Bitwarden CLI. Ask the owner, or use: bwenv list`
  - a reading command with a secret path among its arguments, or a `<`, `>` or `>>` redirection
    (attached or separate) to or from a secret path:
    `${path} holds secrets. Use: bwenv list (names only, no values)`

- [ ] **Step 1: Write the failing tests.** These are table-driven in `test/guard.test.ts`, inside a
  sandbox whose manifest declares `~/.k` and `.dev.vars`, and whose state records `~/.other`.
  - **Denied:**
    - `cat .dev.vars`
    - `grep X ~/.k`
    - `cp .env /tmp/x`
    - `echo hi > .dev.vars`
    - `sort <.env`
    - `cat "$HOME/.k"`
    - `head ${HOME}/.other`
    - `FOO=1 cat .dev.vars`
    - `ls && cat .dev.vars`
    - `bw list items`
    - `/opt/homebrew/bin/bw get password x`
  - **Allowed:**
    - `set -a && . ~/.k && set +a`
    - `source .dev.vars`
    - `bun --env-file=$HOME/.k x.ts`
    - `git check-ignore .dev.vars`
    - `ls -la .dev.vars`
    - `test -f .env`
    - `chmod 600 .env`
    - `bwenv list --file .dev.vars`
    - `cat README.md`
    - `cat .env.example`
  - `judgeToolCall`:
    - `Read` of `<project>/.dev.vars` is denied;
    - `Read` of `~/.other`, from a cwd that has no manifest, is denied through the state;
    - `Edit` of `.env` is denied;
    - `Grep` with `path: '.dev.vars'` is denied;

    - garbage stdin exits 0;
