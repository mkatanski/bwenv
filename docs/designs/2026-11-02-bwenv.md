# bwenv — local secret files, backed by a private Bitwarden vault

Status: design, awaiting approval · 2026-11-02, revised 2026-11-03 after a builder check

## Why

A project's local secret files were lost. Nothing recorded which variables existed, which file
each one lived in, or how to make a new one, so recovering meant reading design documents to rebuild
the list. The values themselves existed nowhere else on this machine.

`bwenv` makes that recoverable in one command, and it is meant for every project:

- the **project repo** records what it needs: each variable's name, its file, and how to make it;
- the **private Bitwarden vault** holds the values;
- the **files on disk** are a copy written from the vault and can be rebuilt at any time.

## Goals

- `bwenv sync` rebuilds every secret file of a project from the vault.
- `bwenv add | update | rm` change a variable in the vault and in its local file in one step.
- `bwenv list` shows which variables a project declares and which are present, **without ever
  printing a value**. It works with the vault locked, so an agent can run it.
- `--env <name>` switches a project's files to another environment's values.
- A Claude Code hook stops an agent from reading or editing a secret file. The hook asks bwenv which
  paths are secret, so it does not rely on patterns hard-coded in the hook.
- One tool for all of the owner's projects, installed once per machine.

## Non-goals

- Pushing values anywhere except the vault and local files. GitHub secrets, hosting-provider secrets and CI
  are out of scope.
- Sharing with other people. Items live in the owner's **private vault**. There is no organization or
  collection support.
- Formats other than `KEY=value` lines: no JSON credential files, no `.npmrc`.
- Two-way sync.

## Anti-goals: these would make it a failure even if it works

- A secret value printed to the terminal, written to a log, or passed in a process's argv where `ps`
  or shell history can see it.
- `sync` silently overwriting a value the owner changed by hand. Losing a value is exactly what this
  tool exists to prevent.
- A secret written into a file inside a repository that git does not ignore.
- A value from one environment silently standing in for another.

## Approaches considered

| Decision | Chosen | Rejected, and why |
|---|---|---|
| Vault access | Wrap the **`bw` CLI** the owner already logs in with (self-hosted server, `bw` 2026.10.1) | Bitwarden Secrets Manager (`bws`): a separate product with machine accounts and an organization, far more than a private vault needs |
| Item shape | **One Login item per variable** (per environment, if the variable varies by environment). The value goes in `login.password` | One secure note per file: changing one variable rewrites the whole note and there is no per-variable history. Secure note per variable: the value shows unmasked in the Bitwarden UI and there is no password history |
| Sync direction | **One way, vault → files.** Writes to the vault happen only through `add`, `update` and `rm`, each of which changes the vault and the file together | Two-way sync: it must decide which side is newer, and a `.dev.vars` file has no history to tell |
| Where the variable list lives | **A `bwenv.json` manifest committed in each project** | List only in the vault: a fresh clone cannot tell what is missing or how to make it, which is the failure that started this |
| Distribution (owner's call) | **`bun link`** from the bwenv checkout: the command points at the sources and an edit takes effect at once | Compiled `bun build --compile` binary: has to be rebuilt after every change. `link:../bwenv` devDependency: a project's CI installs from a clean checkout, where `../bwenv` does not exist |

## Constraints

- **TypeScript, run by Bun** (1.4.4 on this machine). No runtime dependencies: only Bun and `node:*`
  built-ins. Dev dependencies: `typescript`, `@types/bun`, `eslint`, `@eslint/js`,
  `typescript-eslint`, `prettier`.
- The owner's rules apply to this repo:
  - no `any` (use `unknown` and narrow);
  - no `eslint-disable` of any kind;
  - `index.ts` files only re-export;
  - comments only where a test or a better name cannot carry the meaning.
- Commits are one Conventional Commits line with **no body, trailer or attribution of any kind**.
- Hosted as the private GitHub repo `mkatanski/bwenv`, checked out at `~/projects/mkatanski/bwenv`.
  The checkout's location selects the commit identity through `includeIf` in `~/.gitconfig`.
- Every `bw` call except `unlock` runs with `--nointeraction --response`. Observed on 2026-11-02:
  without those flags a locked vault makes even `bw get template item` prompt for the master password,
  and with no TTY it crashes. With them it returns `{"success":false,"message":"Vault is locked."}` and
  exits 1.
- The session key reaches `bw` through the `BW_SESSION` environment variable of the child process,
  never through `--session`, which would put it in argv. Encoded item JSON is piped to `bw create` and
  `bw edit` on stdin (both read stdin), never passed as an argument.

## How it works

### The manifest: `bwenv.json` at the project root

```json
{
  "project": "my-app",
  "defaultEnvironment": "local",
  "variables": {
    "API_KEY": {
      "file": "~/.my-app-keys",
      "how": "the provider's dashboard → Settings → API Keys → Create Key"
    },
    "AUDIENCE_ID": {
      "file": ".dev.vars",
      "perEnvironment": true,
      "how": "the provider's dashboard → Audiences → the environment's audience"
    }
  }
}
```

**Fields:**

- `project` names the project in the vault. It must match `^[a-z0-9][a-z0-9-]*$`.
- `defaultEnvironment` is optional and defaults to `local`. It matters only for variables marked
  `perEnvironment`.
- Each variable name must match `^[A-Z_][A-Z0-9_]*$`.
- `file` is either `~/…`, relative to the home directory and shared by every checkout, or a path
  relative to the manifest's directory, which belongs to that checkout, so each git worktree has its
  own. Absolute paths are rejected because they would tie the manifest to one machine.
- `how` is free text, shown when a value is missing.
- `perEnvironment` defaults to `false`.

**The schema has no arrays, on purpose.** The tool rewrites this file (`add` and `rm`) as
`JSON.stringify(manifest, null, 2)` plus a trailing newline. With objects and strings only, that
output is already Prettier-stable. If a project's Prettier check covers `*.json` at its root, an
array would be reflowed by Prettier and fail the check.

The manifest is found by walking up from the current directory. Under `pnpm <script>` the current
directory is the package root.

### The vault layout

- Folder: `bwenv/<project>`. bwenv creates it on first write.
- An item for a shared variable is named `<project>/<NAME>`. An item for a `perEnvironment` variable is
  named `<project>/<env>/<NAME>`. A variable name cannot contain `/`, so the two forms never collide.
- Item type: Login. `login.username` is the variable name and `login.password` is the value. `notes`
  holds the `how` text and a line saying which project and file the item belongs to. The notes exist
  so the item makes sense when someone browses the vault by hand.
- Items are looked up with one `bw list items --folderid <id>` call per run, matched on the exact
  name in code. They are never looked up with `bw get` by search term, which fails when more than one
  item matches.

### The session

**An agent never touches the vault** (owner's decision, 2026-11-03). A `BW_SESSION` exported in the
shell that starts Claude Code is inherited by every agent, and it opens the whole private vault, not
only bwenv's folder. So when `CLAUDECODE=1` is set in the environment (Claude Code sets it in its
Bash tool, observed on 2026-11-03), bwenv refuses `sync`, `add`, `update`, `rm` and `list --vault`
before calling `bw` at all. The message names the command for the owner to run themselves. An agent
can still run `list` without `--vault`, `is-secret` and `hook`, none of which touches the vault. The
hook also denies `bw` itself (see `bwenv hook claude`).

Otherwise:

1. `bw status` reports `unauthenticated`: stop, and tell the owner to run `bw login`.
2. `BW_SESSION` is set and `bw status` reports `unlocked`: use it. bwenv **never unlocks when a valid
   session exists**, because `bw unlock` invalidates every earlier session key.
3. The vault is locked and stdin is a TTY: run `bw unlock --raw` with stdin and stderr inherited and
   stdout captured. bw writes its prompt to stderr, which is what makes `$(bw unlock --raw)` work in a
   shell. Keep the key in memory for this run only. Then print one line suggesting
   `export BW_SESSION=$(bw unlock --raw)` so later commands do not ask again.
4. The vault is locked and there is no TTY, for example when an agent runs it: stop with that same
   export line. Never hang.

bwenv does not store the session key anywhere.

`bw sync` runs once at the start of every command that touches the vault, because the local `bw`
cache can be hours old.

### Local files

- Format: one `KEY=value` per line. The same file is read by `bun --env-file`, by wrangler's
  `.dev.vars` loader, by a shell `. file`, and by hand-written loaders, which take the raw
  text after `KEY=` and do **no unquoting**. One format has to satisfy all of them, so **values are
  never quoted**. Instead, a value must match `^[A-Za-z0-9_\-.:/@+=,%]+$`, and bwenv refuses anything
  else with a message saying why. API tokens, IDs and email addresses all fit.
- Writes keep every line bwenv does not own, comments included. bwenv replaces a key's line where it
  already is and appends a new key at the end.
- Each write goes to a temporary file in the same directory and is then renamed over the target.
  Mode is `0600`.
- A file inside a git work tree is written only if `git check-ignore -q <path>` succeeds. If it does
  not, bwenv refuses and says to add the file to `.gitignore` first. Files outside any work tree,
  such as `~/…`, skip the check.

### State: what bwenv last wrote

`$XDG_STATE_HOME/bwenv/state.json` (default `~/.local/state/bwenv/state.json`), mode `0600`. It is
keyed by absolute file path:

```json
{ "/Users/me/projects/x/.dev.vars": { "project": "x", "environment": "local",
    "values": { "API_KEY": "<sha256 hex of the value>" } } }
```

It answers two questions:

- whether a value on disk was changed by hand since bwenv wrote it;
- which environment a file currently holds.

Hashes, not values. A hash of a low-entropy value such as an ID or an email address could be guessed,
which is acceptable because those values are not secret.

### Commands

None of them prints a value. Exit codes: `0` success, `1` something needs attention (a conflict,
a missing value), `2` wrong usage.

**`bwenv sync [--env <name>] [--file <path>] [--force]`**

Writes every declared variable, or only those of one file, from the vault to its file.
`--env` defaults to `defaultEnvironment`, and the choice is **not sticky**: a plain `sync` always
means the default environment. Each variable lands in one of these outcomes:

| Situation | What happens |
|---|---|
| File value equals the vault value | Nothing to write |
| File value equals what bwenv last wrote, or the key is absent from the file | Written from the vault |
| File value differs from both the vault and bwenv's last write, **or** there is no record and it differs from the vault | **Conflict.** Left untouched and reported. The report offers `bwenv update NAME --from-file` to keep the local value, or `--force` to take the vault's |
| No item in the vault | Left untouched and reported with the `how` text and the `bwenv add NAME` command. A local value may be the only copy, so it is never deleted |
| `perEnvironment` and no item for that environment | Reported as missing. The value is **never** taken from another environment |

Everything that is not a conflict is still written. The command exits 1 if anything was reported.

**`bwenv add <NAME> [--file <path>] [--env <name>] [--from-file] [--how <text>]`**

Creates the vault item, writes the file, and records the variable in the manifest when it is new.

- **The value** comes from a hidden prompt. If stdin is not a TTY, it is read from stdin, so
  `pbpaste | bwenv add X` works. It is **never taken from argv**. With `--from-file` the value comes
  from the variable's file instead, which is how a project's existing files get onto the vault for
  the first time.
- **A name not yet in the manifest** requires `--file` and gains an entry. Passing `--env` marks the
  new variable `perEnvironment`. `--how` fills its hint.
- **A name already in the manifest** together with a different `--file` is refused.
- **An item that already exists** is refused, with the message pointing to `update`.
- **Order of writes:** the vault first, then the file, then the manifest. If the vault write fails,
  nothing else is written.
- **The file is written only when it holds the same environment.** That means the target environment
  matches the file's environment in the state, or there is no state and the target is the default
  environment. Otherwise only the vault changes, and the output says so.

**`bwenv update <NAME> [--env <name>] [--from-file]`**

Replaces the value of an existing item. The value is read the same way as in `add`. The previous
value must stay recoverable from the item's password history. **This needs checking:** if `bw edit
item` does not record password history itself, bwenv appends the old value to `passwordHistory` in the
JSON it sends. The file follows the same environment rule as in `add`.

**`bwenv rm <NAME> [--env <name>] [--yes]`**

- **With `--env`, on a `perEnvironment` variable:** deletes only that environment's item.
- **Otherwise:** deletes every item of the variable, its line in the file, and its manifest entry.

Items go to the Bitwarden **trash**, never `--permanent`, and the output says they can be restored
for 30 days. On a TTY bwenv asks before deleting. Without a TTY it needs `--yes`.

**`bwenv list [--file <path>] [--vault]`**

Reads the manifest, the files and the state, and does not touch the vault. For each file it shows:

- each declared variable, `set` or `missing`, with the `how` text for missing ones;
- the environment the file was last synced from;
- keys present in the file that the manifest does not declare.

`--vault` also opens the vault and adds a column per variable: `same`, `differs` or `not in vault`.

**`bwenv is-secret <path>`** exits 0 if the path is a secret file and 1 if it is not. A path counts as
secret if any of these holds:

- it is a `file` in the manifest found from the current directory;
- it is a `file` in the manifest found by walking up from the path itself;
- it is a path recorded in the state file. This covers every file bwenv has ever written on this
  machine, so `~/.my-app-keys` stays protected while an agent works in any other repository;
- its name is `.env`, `.env.*` except `.env.example`, `.dev.vars` or `.dev.vars.*`, whether or not a
  manifest declares it.

**`bwenv hook claude`** is a Claude Code `PreToolUse` hook. It reads the hook's JSON from stdin and
answers with a deny decision when the tool would read or write a secret path:

- `Read`, `Edit`, `Write`, `NotebookEdit`: on `file_path`.
- `Grep`: on `path`.
- `Bash`: the command is split on `|`, `&&`, `||`, `;` and newlines, and each segment is judged on
  its own.
  - **Denied:** a segment whose command is `bw`. Agents never touch the vault.
  - **Denied:** a segment that **reads or writes the contents** of a secret path. That means its
    command is one of `cat`, `less`, `more`, `head`, `tail`, `grep`, `rg`, `ag`, `sed`, `awk`, `cut`,
    `sort`, `uniq`, `diff`, `cmp`, `bat`, `xxd`, `od`, `hexdump`, `strings`, `base64`, `cp`, `mv`,
    `tee`, `jq`, `vi`, `vim`, `nvim`, `nano`, `code`, `open` or `pbcopy` with a secret path among its
    arguments, or the segment has a `<`, `>` or `>>` redirection to or from a secret path.
  - **Allowed:** everything else, including:
    - `bwenv` itself;
    - `.` and `source`, which use a file without printing it, as in `set -a && . ~/.my-app-keys`;
    - `bun --env-file=…`;
    - `git check-ignore`, `ls`, `test -f` and `chmod`.
  - **Before a word is resolved to a path:** `~`, `$HOME` and `${HOME}` are expanded,
    `--flag=value` is split at the first `=`, and surrounding quotes are removed.
  - The denial message points to `bwenv list`.

This is a guardrail against accidents, not a lock: a shell command can always be written so that it
reads a file without naming it. Registering the hook in `~/.claude/settings.json` is a separate step,
taken through chezmoi, because that file is managed there.

### Messages

Every error says what to do next in plain words, and names the variable and the file, never the value.
For example: `API_KEY is not in Bitwarden yet. Make one at example.com → API Keys,
then run: bwenv add API_KEY`.

### Testing

- `bun test`. Unit tests cover the manifest, dotenv merge, path resolution, the guard and the
  sync decision table.
- Integration tests run the real CLI as a subprocess against a **fake `bw`**: an executable script
  that keeps a vault in a JSON file and imitates `--nointeraction --response`, locked and
  unauthenticated states included. bwenv runs whatever `BWENV_BW` names, defaulting to `bw`. `HOME`
  and `XDG_STATE_HOME` point at temporary directories.
- One manual smoke test against the real vault, run by the owner because only the owner can unlock
  it. It checks three things the fake cannot prove:
  - the shapes `bw` really returns;
  - the `unlock` prompt;
  - password history on `update`.
